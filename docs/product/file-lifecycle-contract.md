# Kairo File lifecycle and document-grounding contract

Status: implementation-ready contract for [Research and specify Kairo document ingestion and viewing](https://github.com/xddinside/kairo/issues/12)

Research date: 8 August 2026

## Scope

This contract covers Markdown and PDF Files from upload through deletion. It covers the original bytes, the derived text used for grounding, native viewing, export, and failure recovery.

It does not add Office files, audio, video, OCR, collaboration, public sharing, or a second application database. Focus interaction design remains in [Redesign Focus and document-assisted sessions](https://github.com/xddinside/kairo/issues/13). The model context and provider runtime must consume this contract but are specified in [Research Kairo model context, agent loop, and production renderer](https://github.com/xddinside/kairo/issues/17).

The current checkout contains prototype routes and no production File service. This document is the target contract for that service; it does not describe the prototype as implemented.

## Fixed inputs and decisions

- A `User` is the only owner. Clerk's user id is the external identity key. A File can link to one owned Course or no Course.
- A `File` is an original Markdown or PDF upload. A `Note` is student-authored Markdown and is a different record. Do not collapse the two types.
- Every File is private. A storage URL that is merely hard to guess is not an access control.
- Use Clerk in TanStack Start server functions or routes, Neon Postgres for metadata and ownership, Drizzle for typed access and checked-in SQL migrations, and Effect services for workflows.
- Use Filebase Free through one Effect `FileStorage` adapter. The adapter is the only code that imports the S3 client or knows Filebase credentials. Vercel Blob remains a provider fallback behind the same interface; changing it must not change the File or grounding contracts.
- Run through the Node boundary on Vercel. The Vercel Function request and response body limit is 4.5 MB, so Kairo does not send original bytes through a Function. The browser uploads and reads through short-lived URLs minted after an owner check.
- Store original bytes. Store derived extraction separately and version it. Never replace an original with parsed HTML, a PDF image, or a model summary.
- A File can supply evidence to a Generated view or Focus view. An inference from a File cannot silently change a Task, Assessment, Timetable entry, Course, Note, or any other shared academic data. It requires Clarification and a typed proposed command.
- Foreign and unknown File ids return the same not-found result. The browser never supplies authority through a File id, Course id, storage key, or owner id.

Primary source decisions are recorded in [Choose Kairo production data and deployment foundation](https://github.com/xddinside/kairo/issues/8), including the later Filebase correction, and [Choose Kairo private file storage](https://github.com/xddinside/kairo/issues/16). The limits below are Kairo application limits, not claims about the provider's maximum object size.

## Contract types

These are domain shapes. The implementation should use Effect Schema and derive TypeScript types from the schemas. Database enum values and API values must use the same strings.

```ts
type FileKind = "markdown" | "pdf";

type FileLifecycleState =
  | "pending_upload" // row exists; object is not trusted or readable
  | "processing" // object verified; parser and chunker are running or queued
  | "ready" // original is viewable and approved chunks may ground a request
  | "failed" // retryable processing or provider failure; object stays quarantined
  | "rejected" // terminal validation or parser rejection; never viewable
  | "deleting"; // hidden from the product while object and rows are removed

type FileExtractionState =
  | "pending"
  | "ready" // all supported text was extracted within the cap
  | "truncated" // File is viewable; only the bounded prefix grounds a request
  | "empty" // valid File, but no selectable text; no grounding
  | "failed"; // retryable extraction failure; no grounding

type FileFailureCode =
  | "upload_expired"
  | "size_mismatch"
  | "unsupported_name"
  | "unsupported_type"
  | "invalid_encoding"
  | "invalid_signature"
  | "damaged_pdf"
  | "pdf_page_limit"
  | "parser_timeout"
  | "parser_memory_limit"
  | "storage_unavailable"
  | "storage_quota"
  | "processing_exhausted"
  | "delete_pending";

type FileRecord = {
  id: string; // UUID, generated by the server
  ownerId: string; // Clerk id; never client supplied
  courseId: string | null;
  kind: FileKind;
  displayName: string;
  contentType: "text/markdown" | "application/pdf";
  sizeBytes: number;
  sha256: string | null; // base64 or lowercase hex; choose one and keep it stable
  storageKey: string; // server-only; never returned to the browser
  state: FileLifecycleState;
  extractionState: FileExtractionState;
  extractionVersion: string | null;
  pageCount: number | null;
  extractedChars: number;
  failureCode: FileFailureCode | null;
  version: number; // optimistic concurrency value
  createdAt: string;
  updatedAt: string;
  readyAt: string | null;
};

type FileSourceLocator =
  | { kind: "markdown_line"; lineStart: number; lineEnd: number }
  | { kind: "pdf_page"; page: number };

type FileGroundingChunk = {
  fileId: string;
  ordinal: number;
  locator: FileSourceLocator;
  text: string;
  extractionVersion: string;
};

type FileGroundingRef = {
  fileId: string;
  locator: FileSourceLocator;
  quoteHash: string; // identifies evidence without putting the quote in a log
};
```

`failed` is retryable and is not a user-visible success. A valid, parser-readable scanned PDF becomes `ready` with `extractionState: "empty"`; OCR is not run. A parser failure that proves the PDF is damaged becomes `rejected`. A timeout or worker crash becomes `failed` so the original can be retried without another upload.

### State transitions

```text
pending_upload -> processing -> ready
pending_upload -> rejected                 (expiry, quota, validation, bad bytes)
processing    -> failed -> processing      (transient failure, bounded retries)
processing    -> rejected                  (unsupported or damaged content)
ready         -> deleting                  (user or account deletion)
failed        -> deleting                  (user or account deletion)
rejected      -> deleting                  (cleanup of the original, if present)
deleting      -> [row removed]             (object delete and database cleanup complete)
```

Only `ready` is available to native viewing and grounding. A verified original in `processing` or `failed` may be offered as a download or included in export, but it is not rendered inline or sent to the model. `rejected` never receives a view or download URL. A `deleting` File is hidden and cannot receive a new URL, Canvas attachment, or grounding reference.

There is no long-lived `deleted` File row. After the object is confirmed gone and the metadata transaction commits, the File row, chunks, and user-visible processing records are removed. A small internal deletion job may retain only an operation id, hashed owner key, storage key, attempt count, and safe error code until cleanup succeeds; it contains no file name, bytes, or extracted text.

## Limits and defaults

These defaults protect the Vercel function, PDF.js worker, database, model context, and the shared Filebase free allowance. They are configuration, not values to scatter through handlers.

| Limit | Default | Rule |
| --- | ---: | --- |
| Markdown original | 5 MiB | Reject a larger declared or verified object. |
| PDF original | 25 MiB | Reject a larger declared or verified object. Direct upload avoids the 4.5 MB Vercel body limit. |
| PDF pages | 500 | Reject after parsing the page count; do not process only a hidden prefix. |
| Extracted text | 2,000,000 Unicode characters | Keep the File viewable; mark `truncated` and ground only the stored chunks. |
| Files per User | 100 live Files | Count `pending_upload`, `processing`, `failed`, and `ready`; do not let abandoned uploads bypass the quota. |
| Live original bytes per User | 500 MiB | Reserve declared size at intent time and release it on rejection or deletion. |
| Upload URL lifetime | 10 minutes | Filebase PUT URLs are bearer URLs and can be reused before expiry; use a unique key and verify completion. |
| View/download URL lifetime | 5 minutes | Reissue after expiry. Existing URLs cannot be revoked at Filebase, so delete first and keep this window short. |
| Pending upload age | 24 hours | Mark expired and delete the object if one exists. |
| Processing attempts | 3 | Retry with jitter for transient failures, then leave `failed` with `processing_exhausted`. |
| Processing deadline | 120 seconds | Abort the worker and retry; never hold a request open for parsing. |
| Per-User processing | 2 concurrent jobs | Avoid one User consuming the worker pool. |
| Global processing | 4 concurrent jobs | Tune from measured Vercel and Neon capacity. |
| Grounding selection | 8 Files, 100 chunks, 80,000 characters per request | The model-runtime contract may choose a stricter provider cap. |
| Chunk target | 4,000 characters, 500-character overlap | Split at paragraph or page boundaries first; never split a UTF-16 surrogate pair. |
| Export URL lifetime | 15 minutes | Export archives are temporary objects and are deleted after 24 hours. |

Filebase's current S3 limits are much larger than these application limits: 5 GB for one PUT, 5 TB for multipart objects, 10,000 multipart parts, and 500 S3 requests per second. Those values do not make a 5 GB student PDF safe for this product. The Filebase free tier currently lists 5 GB storage, 5 GB monthly S3 bandwidth, 1 million Class A operations, 10 million Class B operations, one bucket, and no card. Exceeding the free storage or bandwidth cap makes the account read-only instead of billing overage. Kairo must enforce its own quota and report provider-capacity errors before the provider becomes read-only. Recheck these figures at deployment against the linked provider pages.

## Storage keys and metadata

Use one private Filebase bucket. Derive `ownerKey` as a short HMAC-SHA-256 of the Clerk user id with a server-only key. Do not put the raw Clerk id or original file name in an object key.

```text
kairo/v1/u/{ownerKey}/f/{fileId}/original
kairo/v1/u/{ownerKey}/x/{exportId}/archive.zip
```

The server generates `fileId`, `exportId`, and the complete key. Keys are immutable. Editing or replacing a File creates a new File and a new key; it never overwrites an existing object. The database stores the provider name, bucket alias, key, and checksum, but the browser sees only the File id and safe display metadata.

The `files` table should contain at least:

- `id`, `owner_id`, optional `course_id`, `kind`, `display_name`, canonical `content_type`, `size_bytes`, `sha256`;
- `storage_provider`, `storage_bucket_alias`, `storage_key`, `object_etag` or provider checksum;
- `lifecycle_state`, `extraction_state`, `extraction_version`, `page_count`, `extracted_chars`;
- `failure_code`, `failure_attempt`, `upload_expires_at`, `ready_at`, `created_at`, `updated_at`, and `version`.

The `file_chunks` table should contain `file_id`, `owner_id` (for cheap policy checks), ordinal, locator JSON, text, character count, extraction version, and timestamps. Index `(owner_id, file_id, ordinal)`. Chunks are derived and replaceable; the original object is not.

The processing outbox/job table should contain a job id, file id, expected File version, job kind, attempt count, available time, lease time, and safe failure code. A worker claims jobs in a transaction, uses a lease, and makes completion idempotent. A duplicated scheduled invocation must not parse or publish a File twice.

Drizzle owns the typed schema and checked-in SQL migrations. Use a transaction for state plus chunk publication: insert or replace all chunks, set the extraction fields, increment `version`, and move to `ready` in one commit. If the transaction fails, no partial chunks are eligible for grounding. Use a runtime database role that does not bypass RLS. The server sets the current Clerk user in the transaction context and the policy checks `owner_id`; application `WHERE owner_id = currentUser` checks remain required for a uniform not-found result.

## Authorization boundary

Every operation starts with a server-side `requireUser` step that calls Clerk's `auth()` and obtains the current `userId`. Never accept `ownerId` from the browser. For a Course link, load the Course in the same owner scope before inserting or updating the File.

| Operation | Required checks | Result for foreign or unknown id |
| --- | --- | --- |
| List | Current User; query `owner_id = currentUser` | Empty list |
| Upload intent | Current User; file kind, name, size, quota, optional owned Course | Validation or quota error |
| Complete | Current User; File is pending, unexpired, and owned; idempotency key | Same result as the original completion |
| Metadata/view/download | Current User; File is owned and in an allowed state | Not found |
| Attach to Canvas | Current User; File is owned and not deleting/rejected; Canvas is owned and writable | Not found |
| Grounding | Current User; every requested File and chunk is owned and eligible | Omit unavailable refs; never query by File id alone |
| Retry processing | Current User; File is `failed`; no more than the retry budget | Not found or typed conflict |
| Delete | Current User; File is owned; idempotency key | Already-deleted is success for the same idempotency key; otherwise not found |
| Export | Current User; export job is owned | Not found |

The storage provider never answers the question “may this User read this File?” It only receives a server-selected key after the database authorization check. Signed URLs are not persisted, logged, or returned from an unauthenticated route.

### CSRF and same-origin checks

When a TanStack Start server function or route uses cookie-backed Clerk authentication, require both the authenticated session and a Kairo CSRF check. For upload intent, upload completion, Canvas attachment, processing retry, view/download URL minting, export creation/status, File deletion, and account deletion:

- require an `Origin` value that exactly matches the configured Kairo origin for the deployment; reject missing, cross-origin, and unlisted preview origins;
- require `Sec-Fetch-Site: same-origin` when the browser supplies Fetch Metadata headers;
- require a server-issued CSRF token in a non-cookie header, bound to the current session and checked with a constant-time comparison; rotate it with the session;
- use `SameSite=Lax` or stricter session cookies, but treat cookie settings as defense in depth rather than the CSRF check;
- do not use `Referer` alone as a fallback, and do not accept a token supplied in a URL or form field;
- apply the same checks to URL-minting reads because a cross-site request could otherwise obtain a private bearer URL even without mutating a File.

The direct Filebase PUT or GET URL is an object capability with a short expiry. It is not a Kairo CSRF token, does not prove the current User, and must never satisfy the CSRF or same-origin check for a TanStack Start operation. If a future server call uses bearer authentication instead of cookies, it still needs the normal authorization check; the CSRF requirement above applies whenever cookies authenticate the call.

## Upload contract

The logical server operations are:

```ts
type CreateUploadIntent = {
  kind: FileKind;
  displayName: string;
  declaredContentType: string;
  declaredSizeBytes: number;
  courseId: string | null;
  clientRequestId: string;
};

type UploadIntent = {
  fileId: string;
  state: "pending_upload";
  putUrl: string;
  putHeaders: { "content-type": string };
  expiresAt: string;
};

type CompleteUpload = {
  fileId: string;
  clientRequestId: string;
};

type CompleteResult = {
  fileId: string;
  state: "processing" | "ready" | "rejected" | "failed";
  extractionState: FileExtractionState;
};
```

### Intent

1. Authenticate with Clerk and derive the User.
2. Normalize the display name for storage in metadata. Keep a safe, bounded display form; do not use it as a key. Reject empty names, path separators, control characters, and names over 180 Unicode characters.
3. Require `.md` or `.markdown` for Markdown and `.pdf` for PDF. Accept `text/markdown` for Markdown and `application/pdf` for PDF. `text/plain` or `application/octet-stream` may be accepted for `.md` only when byte validation proves UTF-8 Markdown; the canonical stored type remains `text/markdown`. Do not trust a browser MIME string.
4. Check the declared size against the per-kind limit and reserve it against the User quota in a transaction. Check the optional Course belongs to the User.
5. Create the `pending_upload` row and an idempotent client request record. Generate the key and a 10-minute Filebase PUT URL with the canonical content type. Do not expose provider credentials.

The server returns the URL and required `Content-Type`; the browser sends the original bytes directly to Filebase. Configure Filebase CORS for the exact preview and production origins, `PUT`, and the required `Content-Type` header. Do not allow `*` with credentials.

### Completion

The browser calls completion after the PUT returns. The server reloads the row under the User scope and performs:

1. Check that the intent is still pending and unexpired. A repeated completion returns the original terminal result.
2. Issue `HeadObject` for the server-generated key. Require the object to exist, have the expected size, have the canonical content type, and provide the Filebase SHA-256 checksum. If Kairo computes a client checksum in a later optimization, compare it; client values never replace the server check.
3. Mark the File `processing` and enqueue one processing job in the same database transaction. The object is still quarantined: no view URL or grounding query can use it until processing commits `ready`.
4. If the object is missing, too large, too small, or has a bad checksum, mark the File `rejected`, release the reserved quota, and issue an idempotent delete. Do not retry a content mismatch.

Filebase PUT signatures are reusable until expiry. A unique key, short expiry, completion state, checksum, and size check make replay harmless. Completion is not a trust boundary for content; the parser is.

## Validation and content inspection

Validate at intent, completion, and processing. The later checks inspect bytes and not only headers.

### Markdown

- Read at most 5 MiB and reject a stream that exceeds the limit.
- Decode with a strict UTF-8 decoder. Reject invalid sequences, NUL bytes, and a byte-order mark only after removing it from the normalized source.
- Normalize CRLF and CR to LF for extraction and rendering. Keep the original object unchanged.
- Parse CommonMark plus the selected GFM extensions with a pinned `remark-parse`/`remark-gfm` pipeline. Do not enable MDX, JSX, arbitrary plugins, or embedded HTML execution.
- A Markdown parser may accept unusual but valid syntax. Parser acceptance is enough for a `ready` File; a parser crash or resource limit is a retryable failure.

### PDF

- Require a `%PDF-` signature in the first 1,024 bytes and parse the complete object with the pinned PDF.js version. The signature check is an early filter, not proof of a valid PDF.
- Read at most 25 MiB and enforce 500 pages after parsing. Reject encrypted/password-required PDFs in v1 unless the product later adds a user-entered password flow; never store a password.
- Extract with PDF.js `getTextContent` per page. Preserve page numbers and item order. Do not run OCR. A PDF with no selectable text is still `ready` for viewing with `extractionState: "empty"`.
- Set `stopAtErrors: true`, `isEvalSupported: false`, leave `enableXfa: false`, disable annotation and form rendering, and do not use a generic viewer that executes PDF actions. Render only the page canvas and an optional text layer. Do not load remote resources named by the PDF.
- A deterministic parse error or page-limit violation is `rejected`. A worker timeout, memory failure, or provider read failure is `failed` and can retry.

No v1 file is declared safe merely because its extension or MIME header looks right. A future malware scanner may be inserted between verification and parsing; it must preserve the same `processing`/`rejected` states and never expose scan results as model instructions.

## Processing and derived text

The completion operation enqueues a processing job. A cron or worker route drains the outbox with leases; it does not parse inside the upload HTTP request. Vercel Cron can deliver a job more than once, so the worker must claim by row lock and expected File version.

For Markdown, derive plain text from the Markdown AST. Preserve headings, list boundaries, code blocks, and line ranges. For PDF, derive one page stream at a time and record each chunk's page locator. Normalize whitespace only for grounding; never rewrite the source shown to the User.

The chunker targets 4,000 characters with 500-character overlap, preferring blank lines and page boundaries. It stops at 2,000,000 characters. A truncated extraction stores complete chunks up to the cap and marks `truncated`; it does not claim that omitted pages were read. Each chunk includes `fileId`, `ordinal`, `locator`, `extractionVersion`, and text.

Publish chunks with a transaction:

1. Confirm the File is still owned, not deleting, and at the expected `version`.
2. Delete old chunks for this extraction version, insert the new chunks, and update extraction fields.
3. Set `ready`, increment `version`, and set `readyAt`.

Any failure before the commit leaves the old chunks unusable and the File in `failed` or `processing`. A repeated worker sees the expected version and returns the existing terminal result.

## Native viewing and download

### Metadata

`/files` lists safe metadata only: File id, display name, kind, size, Course name if owned, lifecycle state, extraction state, page count, and timestamps. Never return the storage key, provider bucket, raw provider error, checksum unless the UI needs it, or a signed URL in a list response.

### Markdown view

The File detail route authenticates, checks ownership, and asks `FileStorage` for a short-lived GET URL. The browser fetches the source over the configured CORS origin, checks the bounded response length, and renders it with `react-markdown` and the pinned GFM pipeline.

The renderer must use `skipHtml: true`, never use `rehype-raw`, and restrict URL protocols to `https` and `mailto` (or render links as inert text). Block `img`, `iframe`, `object`, `embed`, `form`, `style`, `script`, and event attributes. If a later plugin emits HTML, pass its output through an explicit `rehype-sanitize` schema. Render links with `rel="noreferrer noopener"` and no automatic network fetch for images.

The source remains Markdown. Kairo does not store generated HTML and does not call `dangerouslySetInnerHTML` for File content.

### PDF view

Use PDF.js display APIs in an app-owned viewer. Load the short-lived Filebase GET URL with range requests and a configured CORS response (`Accept-Ranges`, `Content-Length`, `Content-Range`, and `Content-Type`). Pass `isEvalSupported: false` and keep `enableXfa: false`; render pages to canvas, use a text layer for selection/search, and keep annotation and form modes disabled. The viewer has page count, page navigation, zoom, loading, and parse-error states; it does not expose arbitrary PDF actions or XFA forms.

Do not proxy a full PDF through a Vercel Function. If a browser cannot use range requests against the provider URL, use an authenticated range proxy with each response kept below 4.5 MB or move the provider adapter; do not silently increase the upload or response limit.

### Download

The server first checks ownership and state, then mints a GET URL with a safe `Content-Disposition: attachment` and a sanitized filename. The URL is held in browser memory only. Send `X-Content-Type-Options: nosniff` from any Kairo response and use the canonical content type. A download is not an authorization token for another File.

## Grounding contract

The model context service receives a typed request, not a storage URL or raw Filebase client. Its logical input and output are:

```ts
type FileGroundingRequest = {
  ownerId: string; // supplied by the server boundary, not the model
  fileIds: string[];
  maxFiles: number;
  maxChunks: number;
  maxCharacters: number;
};

type FileGroundingResult = {
  chunks: FileGroundingChunk[];
  unavailable: Array<{ fileId: string; reason: "not_found" | "not_ready" | "no_text" }>;
};
```

The service:

- scopes every File and chunk query to the current User;
- accepts only `ready` Files with extraction state `ready` or `truncated`;
- returns `empty` for a valid scanned PDF and does not attempt OCR;
- applies the stricter of the request cap and the model-runtime cap;
- preserves source locators so a Generated view or Clarification can cite a File and page or line range;
- treats all extracted text as untrusted evidence. File text cannot issue a tool call, choose an Action, or override the system or User request;
- does not send storage URLs, raw Filebase metadata, provider errors, or hidden parser traces to the model;
- returns an unavailable reference when a File was deleted after an immutable Generated view was created. The view spec remains unchanged, as required by the Canvas contract.

Selecting a File as context does not itself write academic data. A summary, quote, plan, or evidence list may be returned in a Generated view. If the model proposes “create a Task from page 4,” the proposed command carries `fileId` and page locator evidence and enters Clarification. The User can accept, reject, or correct it in free text. No inferred File fact is committed before that answer. A direct, explicit User instruction remains governed by the Canvas Domain command contract.

Canvas attachment activities store File ids and the state observed at attachment time. They do not copy bytes or extracted text. Uploading from Canvas home still saves the Canvas according to the Canvas contract; generation waits for the File to become eligible or enters recovery with a clear processing state.

## Export

Export is an asynchronous owned job because a ZIP containing original files can exceed Vercel's response limit.

```ts
type ExportJobState = "queued" | "running" | "ready" | "failed" | "expired";

type ExportJob = {
  id: string;
  ownerId: string;
  includeStructuredData: boolean;
  includeNotes: boolean;
  includeFiles: boolean;
  state: ExportJobState;
  archiveKey: string | null; // server-only
  failureCode: string | null; // safe code only
  createdAt: string;
  expiresAt: string | null;
};
```

1. The server authenticates and creates one idempotent `ExportJob` per client request.
2. A worker writes a ZIP to the provider export key. Include `academic-data.json`, Markdown Notes as `.md`, a `files/manifest.json`, and each available original File under a path derived from File id plus a sanitized display name. Never use a raw display name as a ZIP path.
3. The manifest includes File id, kind, display name, size, checksum, Course id, and one of `included`, `unavailable`, or `rejected`. Do not silently omit a File. A transient provider failure makes the export `failed` and retryable.
4. After the archive is complete and committed, the server mints a 15-minute GET URL after checking the export job owner. Do not return provider credentials or keep the URL in the database.
5. A daily cleanup job deletes expired export objects and marks jobs `expired`. Export objects are not part of the User's live File list and are not used for grounding.

Per-File download uses the normal owner-checked view/download flow. Account export includes valid original bytes, including a verified File in `processing` or retryable `failed`; it excludes `pending_upload` and `rejected` objects and records their state in the manifest.

## Deletion

File deletion is permanent in the product and idempotent.

1. Authenticate, load the File under the User scope, and lock its version. Mark it `deleting`, clear its eligibility, and reject new view, download, attachment, retry, and grounding requests. Commit before contacting storage.
2. Issue `DeleteObject` for the exact immutable key. Filebase treats delete as idempotent; a missing object is success. Do not delete by a user-supplied prefix.
3. Delete chunks and the File row in a transaction. Release the User's reserved/live byte count and remove Canvas attachment link rows according to the Canvas contract.
4. If the provider call or final database transaction fails, retain only the hidden `deleting` row and a retryable deletion job. The User receives a recoverable failure, not a false success. The cleanup worker retries with backoff and maps a missing object to success.
5. When the row is removed, no Kairo route can resolve the File. Existing signed URLs may work until their short expiry; Kairo cannot revoke a Filebase presigned URL, which is why read URLs are five minutes and deletion stops all new URL issuance first.

Account deletion uses the same workflow for every owned File and Canvas. It first revokes product access, then queues object deletion and database cascades. It must not report complete while owned File objects remain pending cleanup. Backup and provider retention rules belong to the operations ticket; v1 has no user-visible restore path or hidden app recovery copy.

## Failure and recovery rules

| Failure | State and user result | Recovery |
| --- | --- | --- |
| Clerk absent or expired | No File operation; same auth/not-found boundary | Sign in again |
| Invalid name, type, size, or quota | No readable object; typed validation error | Correct input and retry |
| Vercel payload too large | Never reaches upload intent for bytes; browser uses direct PUT | Retry direct upload; no server proxy |
| PUT timeout or expired URL | `pending_upload`, then `rejected` after 24 hours | Request a new intent; cleanup old key |
| Missing, oversized, or checksum-mismatched object | `rejected`; object delete requested | Upload again |
| Filebase `503 Slow Down` or network timeout | `failed` or job lease retry | Exponential backoff with jitter, max three processing attempts |
| Filebase free cap `403` | Typed `storage_quota`; do not spin on retries | User deletes Files or operator upgrades provider |
| Malformed or password-protected PDF | `rejected`; no view or grounding | User exports/re-uploads an unprotected valid PDF |
| PDF parser timeout or worker crash | `failed`; original remains quarantined | User or worker retries, max three attempts |
| Valid scanned PDF | `ready` + `empty`; native view works | No OCR in v1 |
| Database commit after processing fails | Keep non-ready state; chunks are not eligible | Retry transaction with same expected version |
| Delete object fails | `deleting`; hidden and no new URLs | Cleanup job retries; never claim deleted early |
| Export member read fails | Export `failed` or manifest entry `unavailable` | Retry export; never omit silently |

Provider errors must be translated to the safe codes above. Raw XML, request URLs, stack traces, and object keys stay in redacted server diagnostics only.

## Observability and redaction

Record one structured event per state transition and job attempt with:

- request id, operation id, File id, export/job id, kind, previous and next state;
- byte count, page count, extraction character count, extraction version, attempt count, latency, and outcome code;
- provider name and provider request id when present, without a signed URL;
- quota snapshot as coarse counters, not another User's data.

Never log or send to Sentry: original bytes, Markdown text, PDF metadata or page text, display names by default, signed URLs, access keys, storage keys, Clerk session tokens, export contents, or model prompts containing File text. Hash or omit Clerk ids in provider and infrastructure logs. Configure Sentry `beforeSend` to strip query strings from URLs and redact request bodies and breadcrumbs. Metrics may count bytes and states but must not contain content.

Alert on pending uploads older than 24 hours, processing jobs older than their deadline, repeated parser failures, deletion backlog, orphan objects, Filebase 403 read-only responses, and per-User or global quota near the configured cap. Keep diagnostics long enough for the operations policy; do not invent a separate File-content retention policy in this contract.

## Focused tests

Implement these tests before calling the File path complete. Use a fake `FileStorage` with private-object behavior, expiry, HEAD metadata, range reads, idempotent delete, and injectable 403/404/503 failures.

### Authorization and storage

- A User cannot list, complete, view, download, attach, ground, retry, delete, or export another User's File. Foreign and unknown ids produce the same result.
- Upload intent chooses a server key, never accepts a client key, pins the content type, reserves quota, and returns a short-lived URL.
- The storage adapter emits no public URL and never receives a raw provider credential in a browser bundle.
- Completion is idempotent; a replay cannot replace an existing key or publish a second processing job.
- A size or checksum mismatch rejects and deletes the object. A missing object is not marked `ready`.
- A Filebase 403 quota error stops retries and produces a typed recovery state; a 503 retries with the same job id.
- A cookie-authenticated cross-site or missing-CSRF request is rejected for upload intent/completion, attachment, retry, view/download URL minting, export, and delete; a Filebase presigned URL cannot bypass that check.

### Markdown

- `.md` and `.markdown` with valid UTF-8 become `ready`; CRLF normalizes only in derived text.
- Invalid UTF-8, NUL bytes, wrong extension, oversized input, and a stream over the cap are rejected.
- Markdown extraction preserves heading/list/code boundaries and line locators.
- `<script>`, raw HTML, event attributes, `javascript:` links, remote images, iframes, and embedded objects do not execute or load in the native renderer.
- GFM behavior is covered for tables, task-list syntax, and strikethrough if those extensions remain enabled.
- The renderer never calls `dangerouslySetInnerHTML`; a future plugin must pass the explicit sanitization test.

### PDF

- A valid text PDF becomes `ready` with page locators and extracted text; a two-page fixture cites page 1 and page 2 separately.
- A valid scanned/image-only PDF becomes `ready` with `empty` extraction and remains viewable without OCR.
- A bad header, malformed structure, password-protected fixture, oversized PDF, and PDF over 500 pages never become `ready`.
- A parser timeout or worker crash becomes retryable `failed` and keeps the original quarantined.
- PDF.js renders a page and text layer with `isEvalSupported: false`, uses range requests, and does not render annotations, forms, XFA, or actions.
- A hostile-PDF fixture containing JavaScript actions or embedded script is opened with `isEvalSupported: false`; no script runs, no external request is made, and annotation, form, and XFA layers remain disabled.
- Invalid or expired signed URLs produce the viewer's safe error state, not a provider error dump.

### Grounding, Clarification, and Canvas

- Only ready, owner-scoped Files with extracted text reach `FileGroundingResult`.
- Empty, failed, rejected, deleting, deleted, and foreign Files are unavailable and do not leak existence.
- Grounding respects file, chunk, character, and provider caps and returns page/line locators.
- Text that says “ignore the system” remains evidence text and cannot invoke a tool or Action.
- A File-derived Task, Assessment, Course, timetable change, or other academic mutation creates Clarification with evidence and does not write before acceptance.
- Deleting a File makes an immutable Generated view show an unavailable reference without changing its saved spec.
- Uploading or attaching a File records the expected Canvas activity and never duplicates the object bytes.

### Export and deletion

- An export contains structured data, Markdown Notes, and original valid File bytes with a manifest; it does not contain signed URLs.
- Export jobs are owner-scoped, idempotent, expire, and delete their temporary archive.
- Deletion hides the File before storage work, is safe to retry after a 404, removes chunks and metadata after object deletion, and never reports success while cleanup is pending.
- Account deletion covers every owned File and does not leave a reachable object under a guessed or old URL after the signed URL window.
